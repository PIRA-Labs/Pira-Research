# PIRA Research Roadmap

**Status:** Living document — updated as experiments complete
**Last updated:** 2026-10-30
**Organization:** PIRA-Labs

---

## Overview

This roadmap translates open questions, unresolved experiments, and architectural
gaps from the Vela/Android/MIAU milestone into a prioritized research plan.

It is NOT a product roadmap. PIRA Android and PIRA Web have their own delivery
plans. This document tracks the **evidence-gathering and experimental work**
that must precede or accompany implementation decisions.

Each item includes:
- **Research question:** What we need to learn
- **Why it matters:** Impact on PIRA architecture or implementation
- **Evidence needed:** What would constitute a verified answer
- **Dependencies:** Prerequisites or blockers
- **Confidence:** Current state of knowledge

## P0 — Immediate (next 4 weeks)

### K-01: Gadgetbridge pairing with Redmi Watch 4

**Research question:** Can Gadgetbridge connect to WATCH-01 using the auth key
obtained during the MIAU milestone?

**Why it matters:** Gadgetbridge is the leading open-source replacement for Mi
Fitness. If it can pair with Redmi Watch 4, it eliminates the feature-gate
problem entirely and gives PIRA a transparent, auditable transport layer.

**Evidence needed:**
- Successful Gadgetbridge → WATCH-01 pairing
- Device info retrieved through Gadgetbridge API
- Confirmation that pairing does not destroy existing Mi Fitness session

**Dependencies:**
- Auth key preserved locally (available)
- Gadgetbridge already built and installed on NODE-01 (verified)
- NODE-01 operational (verified)

**Confidence:** Medium. Auth key acquisition succeeded. Pairing was not
completed before lab closed.

**Success criterion:** Gadgetbridge shows WATCH-01 as a connected device.

**Fallback:** If Gadgetbridge cannot pair, the exact failure mode will
determine next steps (protocol mismatch, auth key format, device firmware
version).

---

### K-02: Persistent authorization store

**Research question:** How should PIRA persist user authorizations across app
restarts without exposing them to compromise?

**Why it matters:** Current `Authorization` objects are in-memory only. An app
restart clears all grants, forcing the user to re-authorize every capability.
This is unusable for an agent runtime.

**Evidence needed:**
- Secure persistent store that survives app restart
- Expiry cleanup mechanism
- Revocation capability
- No credential leakage in logs or backups

**Dependencies:**
- SecureKeyStore already implemented (AES-GCM, Android Keystore)
- PolicyEngine authorization flow already defined

**Confidence:** High that the design is straightforward. Implementation
complexity is in the UX (revocation UI, expiry handling).

**Success criterion:** Authorizations persist across app restart; expired
grants are cleaned up; user can revoke from UI.

---

### K-03: Keystore hardware backing verification

**Research question:** Is the AES-GCM key generated by `SecureKeyStore` backed
by hardware (StrongBox or TEE) on NODE-01 and other target devices?

**Why it matters:** If the key is software-backed, a device compromise could
extract it and decrypt stored credentials. Hardware backing is a requirement
for the threat model.

**Evidence needed:**
- `KeyInfo` query showing `isInsideSecureHardware = true` or
  `isStrongBoxBacked = true`
- Behavior documented on devices without StrongBox
- Fallback strategy if hardware backing unavailable

**Dependencies:**
- NODE-01 or equivalent test device
- PIRA Android debug build with KeyInfo logging

**Confidence:** Low. Not yet tested on any device.

**Success criterion:** Clear report of hardware backing status on at least
one target device, with documented fallback.

## P1 — Near-term (1–3 months)

### K-04: Watch→phone via public API (if feature gate is bypassed)

**Research question:** Is there a path for WATCH-01 to send arbitrary payloads
to NODE-01 through the XMS public API, bypassing the `isSupportThirdPartyApp`
gate?

**Why it matters:** The MIAU log bridge is a prototype. A proper API path is
required for production. The feature gate is the known blocker.

**Evidence needed:**
- One of:
  - Xiaomi updates the feature list for Redmi Watch 4
  - A new API surface is discovered that bypasses the gate
  - Gadgetbridge provides an alternative transport
  - Direct BLE protocol implementation succeeds

**Dependencies:**
- K-01 (Gadgetbridge pairing) as primary alternative path
- Continued monitoring of Mi Fitness updates
- Protocol analysis from existing decompilation

**Confidence:** Low via public API. Medium via alternative transport.

**Success criterion:** A watch-generated payload reaches PIRA Android through
a reproducible, non-prototype path.

---

### K-05: Dynamic capability registry

**Research question:** Can PIRA's capability set be extended at runtime without
app redeployment, while maintaining the deny-by-default guarantee?

**Why it matters:** The current `Capability` enum is hardcoded. As PIRA
integrates more device capabilities (sensors, wearables, appliances), a
hardcoded allowlist becomes unmaintainable.

**Evidence needed:**
- Capability schema format (typed, with parameter specifications)
- Policy module that can load new capabilities without app restart
- Audit trail for capability registration
- Deny-by-default guarantee preserved for unregistered capabilities

**Dependencies:**
- K-02 (persistent authorization store) for grant persistence
- PolicyEngine refactoring from monolithic to modular

**Confidence:** Medium. The design is conceptually clear; implementation
requires careful security review.

**Success criterion:** New capability can be registered by policy update and
immediately enforced by the runtime.

---

### K-06: Process isolation for PolicyEngine

**Research question:** Can PIRA's `PolicyEngine` run in a separate process or
sandbox, preventing a compromised UI component from manipulating policy state?

**Why it matters:** Currently `PiraRuntime` and `MainActivity` share a process.
If the UI is compromised (e.g., via a malicious view injection), an attacker
could call `policy.evaluate()` with crafted proposals or tamper with the
emergency stop flag.

**Evidence needed:**
- Separate process or service implementation
- IPC mechanism with capability restrictions
- Performance impact measurement
- Security boundary verification

**Dependencies:**
- Modular PolicyEngine architecture (from K-05)
- Android Service or isolatedProcess implementation

**Confidence:** Medium. Android supports `android:process` and
`android:isolatedProcess`, but the latter has significant limitations.

**Success criterion:** PolicyEngine runs in a separate process; UI can request
evaluations but cannot directly modify policy state.

## P2 — Medium-term (3–6 months)

### K-07: Semantic proposal validation

**Research question:** Beyond parameter allowlisting, can PIRA validate the
_semantic intent_ of an `ActionProposal` before execution?

**Why it matters:** The current parameter allowlist (`"prompt"`, `"message"`)
prevents arbitrary parameter injection. But an agent could craft a proposal
that passes the allowlist while executing a harmful action — e.g., a camera
proposal with a legitimate-looking `"prompt"` parameter that triggers
unexpected behavior.

**Evidence needed:**
- Proposal schema with semantic constraints (ranges, formats, enums)
- Validation layer that checks parameter values, not just keys
- Test cases with adversarial proposals
- Performance impact on policy evaluation latency

**Dependencies:**
- Dynamic capability registry (K-05)
- Structured logging for validation failures

**Confidence:** Medium. The approach is standard in authorization systems
(RBAC/ABAC), but the threat model for agent-generated proposals is less
studied.

**Success criterion:** A set of adversarial proposals that pass the current
allowlist are caught by semantic validation.

---

### K-08: Vela black-screen root cause

**Research question:** Why does a from-scratch Vela Quick App black-screen on
Redmi Watch 4, while a Songbird-derived structure opens correctly?

**Why it matters:** Understanding the renderer boundary prevents future
wasted debugging sessions and enables faster Vela app development.

**Evidence needed:**
- Systematic comparison of working vs. black-screen RPKs
- Minimum viable structure identified
- Documentation of renderer requirements

**Dependencies:**
- Vela toolchain still functional
- Both working and broken RPKs available for comparison

**Confidence:** Low. Root cause was not identified during the milestone.

**Success criterion:** A from-scratch minimal Vela app that opens correctly,
with documented structural requirements.

---

### K-09: Direct BLE protocol implementation

**Research question:** Can PIRA implement direct BLE communication with
WATCH-01, bypassing both Mi Fitness and Gadgetbridge?

**Why it matters:** Both Mi Fitness and Gadgetbridge are external dependencies.
A direct BLE protocol would give PIRA full control over the transport layer
and eliminate the feature-gate problem permanently.

**Evidence needed:**
- BLE GATT service/characteristic discovery on WATCH-01
- Prototype that sends and receives raw BLE packets
- Comparison with XMS protocol behavior
- Battery/performance impact

**Dependencies:**
- BLE scanning and GATT APIs on Android
- Protocol analysis from MIAU milestone (packet structure known)
- WATCH-01 available for testing

**Confidence:** Low. Direct BLE on Xiaomi wearables often requires
proprietary service UUIDs and authentication. This is a long-term research
direction, not a near-term plan.

**Success criterion:** One arbitrary payload sent from NODE-01 to WATCH-01
via raw BLE without Mi Fitness or Gadgetbridge.

## P3 — Long-term (6+ months)

### K-10: Watch microphone access from Vela Quick App

**Research question:** Can a Vela Quick App access the watch microphone for
push-to-talk or continuous audio capture?

**Why it matters:** Voice is a natural interface for an agent. If the watch
can capture audio, it becomes a more capable remote interface for Pantera.

**Evidence needed:**
- Vela API documentation or empirical test of microphone access
- Audio capture → phone → agent pipeline
- Privacy model (when is the mic active, user control)

**Dependencies:**
- Working watch→phone transport (K-04 or K-09)
- Vela API investigation

**Confidence:** Low. Vela Quick App API surface is limited and poorly
documented. Microphone access may require native extensions or may be
unavailable.

**Success criterion:** One audio frame captured on watch and received on
phone.

---

### K-11: Multi-user consent model

**Research question:** How does PIRA handle consent when multiple users
interact with the same physical device?

**Why it matters:** PIRA is designed as a personal agent runtime, but the
Android device may be shared. The current model assumes a single user.

**Evidence needed:**
- Use cases: shared household device, multiple agents, guest access
- Consent flow design
- Authorization isolation between users
- Privacy implications

**Dependencies:**
- Persistent authorization store (K-02)
- PolicyEngine modular architecture (K-05)

**Confidence:** Low. No existing research in this direction.

**Success criterion:** Design document for multi-user consent with at least
two distinct user profiles.

---

### K-12: Credential rotation

**Research question:** How should PIRA handle Nebius API key rotation without
requiring manual re-entry?

**Why it matters:** API keys expire or get compromised. Manual re-entry is
error-prone and interrupts agent operation.

**Evidence needed:**
- Key rotation flow design
- Secure key update mechanism
- Grace period for old keys during rotation
- Audit trail for rotation events

**Dependencies:**
- SecureKeyStore (implemented)
- NebiusClient key management (implemented)

**Confidence:** Low. Not yet investigated.

**Success criterion:** Automated key rotation flow that updates the stored
credential without user intervention.

---

### K-13: Watch→HTTP direct networking

**Research question:** Can WATCH-01 make direct HTTP requests to NODE-01 or
a cloud endpoint without a phone bridge?

**Why it matters:** Direct networking would simplify the architecture and
reduce latency. It would also make the watch more autonomous.

**Evidence needed:**
- Vela networking API availability
- HTTP client implementation in Vela Quick App
- TLS/certificate handling
- Network performance and battery impact

**Dependencies:**
- Vela API investigation
- NODE-01 with accessible endpoint (Tailscale or local network)

**Confidence:** Very low. Current evidence suggests Redmi Watch 4 does not
expose standard HTTP networking to Vela Quick Apps.

**Success criterion:** One HTTP GET from WATCH-01 to NODE-01 reaching the
server and receiving a response.

## Research Themes

### Theme A: Transport independence

**Goal:** Decouple PIRA from closed vendor transports (Mi Fitness, XMS).

**Research items:** K-01, K-04, K-09
**Success criterion:** PIRA can communicate with WATCH-01 through at least
one open-source or direct-protocol transport.

### Theme B: Runtime hardening

**Goal:** Strengthen PIRA's trust boundary against compromise and misuse.

**Research items:** K-03, K-06, K-07, K-12
**Success criterion:** PIRA passes a structured security review with no
critical findings in the policy engine, credential storage, or audit trail.

### Theme C: Capability extensibility

**Goal:** Allow PIRA to integrate new device capabilities without app
redeployment or security regressions.

**Research items:** K-05, K-11
**Success criterion:** Three new capabilities integrated through policy
updates alone, with full audit trail and user consent.

### Theme D: Wearable autonomy

**Goal:** Increase WATCH-01's capability as an independent interface to
Pantera, while maintaining the thin-client architecture.

**Research items:** K-08, K-10, K-13
**Success criterion:** WATCH-01 can initiate and receive meaningful
interactions with Pantera without requiring phone-app modifications for
each new feature.

## Execution Principles

1. **Evidence before implementation.** No PIRA feature is finalized without
   physical verification on target hardware.

2. **One unknown at a time.** Each experiment changes exactly one boundary.

3. **Preserve checkpoints.** Before any destructive operation (unpair, wipe,
   unlock), save keys, logs, versions, pairing state, and backups.

4. **Close branches explicitly.** Every investigation ends in PROVEN,
   DISPROVEN, BLOCKED, or CLOSED — never indefinitely open.

5. **Publish findings, not just successes.** Failed experiments are research
   output. Document them.

6. **Security review before promotion.** Any finding that influences the trust
   boundary undergoes structured review before affecting PIRA code.

7. **No credential exposure.** Keys, tokens, and pairing secrets never enter
   Git, logs, or published documents.
